# Cross-reference: tconnectsync `events.py` vs TandemKit `Sources/TandemCore/Messages/HistoryLog`

Comparison of the two independent parsers of the Tandem pump history-log record format:

- **Python**: [`tconnectsync/eventparser/events.py`](https://github.com/jwoglom/tconnectsync/blob/master/tconnectsync/eventparser/events.py) (autogenerated, master branch)
- **Swift**: [`Sources/TandemCore/Messages/HistoryLog`](https://github.com/jwoglom/TandemKit/tree/dev/Sources/TandemCore/Messages/HistoryLog) (dev branch)

Each comparison was performed per event type ID by a dedicated analysis agent reading both sources.

## Record layout & methodology

Both parsers consume a 26-byte event record: bytes 0–1 = event type ID, 2–5 = pump timestamp, 6–9 = sequence number, payload at bytes 10–25. Offsets below are absolute within the record and directly comparable.

**Endianness is intentionally different and is NOT reported as an inconsistency**: tconnectsync parses big-endian records from the t:connect cloud export (`'>H'`, `'>I'`, `'>f'`), while TandemKit's `Bytes` helpers (`readShort`, `readUint32`, `readFloat`) parse little-endian BLE payloads.

Field-name differences alone (e.g. `idp` vs `insulinDeliveryProfile`) are noted but not counted as inconsistencies; only offset, width/signedness, missing-field, and enum/value-map differences are.

## Coverage differences

- Every one of the 59 event IDs in tconnectsync `EVENT_IDS` has a TandemKit counterpart; **no event is missing from TandemKit**.
- TandemKit implements **73 additional typeIds** that tconnectsync does not parse (see appendix).
- **Duplicate typeId in TandemKit**: both `CGMHistoryLog` and `DexcomG6CGMHistoryLog` declare `typeId = 256`. `HistoryLogParser` only dispatches `DexcomG6CGMHistoryLog`; `CGMHistoryLog` is dead code (never referenced by the parser).

## Per-event field cross-reference

### ID 3 — LID_BASAL_RATE_CHANGE

`LidBasalRateChange` (py) ↔ `BasalRateChangeHistoryLog` (swift) — severity: **🔴 major**

| Concept | py field | py offset | py type | swift field | swift offset | swift type | Status | Notes |
|---|---|---:|---|---|---:|---|---|---|
| commandedBasalRate | `commandedBasalRate` | 10 | float32 | `commandBasalRate` | 10 | float32 (readFloat) | ✅ match | Name differs trivially (commandedBasalRate vs commandBasalRate); same offset/type. |
| baseBasalRate | `baseBasalRate` | 14 | float32 | `baseBasalRate` | 14 | float32 (readFloat) | ✅ match |  |
| maxBasalRate | `maxBasalRate` | 18 | float32 | `maxBasalRate` | 18 | float32 (readFloat) | ✅ match |  |
| idp (insulin delivery profile) | `idp` | 24 | uint16 | `insulinDeliveryProfile` | 22 | uint16 (readShort) | ❌ offset-mismatch | idp: py uint16@24 vs swift uint16@22. Same width/signedness, different absolute offset. Swift buildCargo also places it at 22 (10+4+4+4 bytes of floats), internally consistent with its init(cargo:). |
| changeType | `changeTypeRaw` | 23 | uint8 | `changeTypeId` | 24 | uint8 (cargo[24]) | ❌ offset-mismatch | changeType: py uint8@23 vs swift uint8@24. The two parsers effectively swap the tail layout: py = changeType@23 then idp@24-25; swift = idp@22-23 then changeType@24 + zero pad@25. Note py idp@24-25 overlaps swift changeType@24. |

**Enum / value-map findings:**

- ⚠️ `changeType value model` — *partial*: Python models changeType as IntFlag bitmask (ChangetypeBitmask, combinable flags); Swift models it as an exclusive enum ChangeType: Int with single rawValue — combined bit values (e.g. 3 = TimedSegment\|NewProfile) decode in Python but return nil from Swift's ChangeType(rawValue:).
- ⚠️ `BasalLimit / basalLimit` — *missing-in-swift*: Python ChangetypeBitmask.BasalLimit = 128 (2**7, ChangetypeMap key "7" = 'basal limit') has no Swift counterpart; Swift ChangeType stops at pumpShutDown = 64.
- ✅ `shared values 1..64` — *match*: timedSegment=1, newProfile=2, tempRateStart=4, tempRateEnd=8, pumpSuspended=16, pumpResumed=32, pumpShutDown=64 agree in name and value across both. Python's ChangetypeMap keys are bit indices 0-7 with prose descriptions; Swift has no description map (doc-only gap).

**Inconsistencies:**

- idp/insulinDeliveryProfile offset mismatch: Python reads uint16 at absolute offset 24 (events.py line 81); Swift reads uint16 at offset 22 (BasalRateChangeHistoryLog.swift line 25, Bytes.readShort(cargo, 22)). Decoded profile ID will differ on any real record.
- changeType offset mismatch: Python reads uint8 at offset 23 (events.py line 82); Swift reads uint8 at offset 24 (cargo[24], line 26). Additionally Python's idp bytes (24-25) overlap Swift's changeType byte (24), so one parser is misreading the tail of the record.
- Swift ChangeType enum is missing basalLimit = 128, present in Python as ChangetypeBitmask.BasalLimit (2**7) / ChangetypeMap key "7" ('basal limit').
- Semantic model difference: Python treats changeType as a bitmask (IntFlag, multiple bits may be set); Swift ChangeType(rawValue:) only decodes exact single power-of-two values and returns nil for combined bitmasks.
